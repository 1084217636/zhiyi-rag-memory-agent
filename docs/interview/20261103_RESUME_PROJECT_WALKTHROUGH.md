# 知忆：按《肖宾_西电_AI软件开发工程师》讲项目

本稿针对 PDF 中的四条项目要点，以 2026-11-03 的 `zhiyi-research-next` 源码及最近实测为准。先背两分钟稿，再用“上传一份研究资料，提出一个问题，跨会话继续研究”的例子讲十分钟。旧 `docs/UPGRADE_INTERVIEW_GUIDE.md` 含 90 项测试等历史数字，不用作最新版背诵材料。

## 1. 开场怎么说

### 两分钟版

> 知忆是我做的个人 AI 研究助手。用户可以在线上传研究资料，等后台解析和建索引后围绕资料提问；系统还能从聊天中提取适合跨会话保留的用户背景、计划或事实，让下一次会话找回这些内容。回答可以带来源引用并保存成可编辑的研究成果。
>
> 我把它分为三条链：文档进入知识库的 RAG 链、对话进入长期记忆的治理链，以及真正回答问题的 Agent 执行链。FastAPI 接收上传和聊天请求，PostgreSQL 保存文档状态、对话、记忆来源和研究成果，Celery 处理解析与记忆抽取；Elasticsearch 保存检索块，Neo4j 保存陈述、实体、关系及来源。模型可选择知识库或记忆工具，但工具范围、用户权限、参数、超时、调用次数和上下文预算由后端控制。涉及私人资料的答案在正式输出前检查证据与引用，失败会修复一次或提示证据不足。
>
> 我专门做了检索、记忆和端到端三层评测：100 篇文档和 100 道标题明确的问题测检索，17 段对话的 100 种问法测 19 组记忆事实，20 份合成文档的 30 题跑真实 Agent/Verifier/SSE；另外有自动化测试。这些集能复现回归，但不能把它们当成开放领域准确率或者宣称“没有幻觉”。

### 十分钟版：按一次实际使用说

1. **用户在线上传（约 1 分钟）**：浏览器把 PDF、DOCX、Markdown、TXT、HTML、CSV 或 XLSX 传到 FastAPI。API 保存文件和 PostgreSQL 文档记录，状态先是待处理；Celery worker 从任务队列接解析任务。解析成功后状态变 `done`，失败变 `failed` 并记录原因。用户可以等状态完成后再问；不是要开发者预先手工把文件灌入 ES。扫描 PDF/OCR、PPT、视频还不属于当前解析范围。
2. **建 RAG 索引（约 1.5 分钟）**：worker 读取文件、按格式解析文本，把标题/段落组织成父块，再切约 256 token 的子块，保留 24 token 重叠；父块目标约 1024 token。对子块算 embedding，把父子块、文档/用户/知识库 ID 和来源位置写 ES。小子块提高定位精度，命中后取父块让模型有足够上下文。PostgreSQL 管文档状态和所有权，ES 管检索，不让 ES 成为文档业务状态唯一来源。
3. **问题检索（约 1.5 分钟）**：用户问“我的实验笔记里 CSI 的采样设置是什么”。`knowledge_search` 在 ES 里强制用当前用户 ID 和启用的知识库过滤，跑向量 kNN 与 BM25 两路召回，再按 RRF 名次融合；若用户配置了 rerank 接口，只对候选少量精排。命中的是子块，交给模型的是父块；引用仍能回指原文档。向量故障可以用 BM25，BM25 故障且向量已有结果可以保留向量；两路不可用时工具报错而不伪装成“资料里没有”。
4. **长期记忆入库（约 2 分钟）**：本轮对话成功后，原聊天留 PostgreSQL；另建立一条带原文、来源消息 ID 与处理状态的 `memories` 记录，交 Celery 后台抽取。输入“我目前研究 WiFi CSI，下个月计划做室内定位实验”，模型先拆成“当前研究 WiFi CSI”和“计划下个月做实验”两条原子陈述，再抽实体、关系与事件。结构化输出用 Pydantic 限字段和分数；原文支持检查不通过的候选不会当作已确认事实。这样不会把“我计划做”直接写成“我已做完”。
5. **记忆去重/冲突（约 1.5 分钟）**：写入前先搜索同一用户相似旧记忆，最多拿 8 条候选；相似度只找比较对象，不决定能否合并。模型在 ADD、NOOP、UPDATE、CONFLICT、SKIP 中提出判断，后端验证目标旧 ID 是否来自本用户候选、置信度及更正条件。完全重复不新增活跃事实；明确更正且通过约束才让旧版本退出活跃召回，并留 `SUPERSEDES` 关系；不明确的冲突进待确认，由用户处理。Neo4j 里有原话 Dialogue→Chunk→Statement 的来源链以及实体关系图。活跃 Statement 预算默认每用户 1000 条，低优先级旧陈述可以归档而不物理抹掉来源。
6. **Agent 回答（约 1.5 分钟）**：FastAPI 取当前会话最近 20 轮，即最多 40 条 user/assistant 消息，再召回少量相关记忆做背景。LangChain 提供消息、模型和 StructuredTool；项目自己组织循环。模型可以不调工具直接回答，也可提出 `knowledge_search`/`memory_search` 等工具。后端校验 Schema、用户范围和参数长度，执行有超时/有限重试，并记录工具结果再交给模型继续。最多 5 次模型工具轮和配置的工具调用预算；上下文按估算 token 数裁掉较旧完整轮次，无法压下去则拒绝本轮。这里没有 LangGraph StateGraph，也没有模型链式思维文本对外展示。
7. **核验与成果（约 1 分钟）**：需要个人资料证据时，后端检查引用 ID 是否存在，再让 verifier 比对关键事实与本轮证据。若不足、冲突或工具故障，有限修复后仍不通过就明确提示依据不足。通过后才用 SSE 发正式回答、工具状态与引用。用户可把回答及引用快照存为 `research_artifacts`，用版本号防止并发覆盖。

## 2. 一张白板图

```text
浏览器上传 ─ FastAPI ─ 文件存储 + PostgreSQL(documents: pending)
                    └─ Redis/Celery → 解析/分块/embedding → Elasticsearch 父子块

浏览器问答 ─ FastAPI ─ PostgreSQL 最近会话 + Neo4j 相关记忆
                   └─ Agent 工具循环 ─ knowledge_search → Elasticsearch
                                    └ memory_search → Neo4j
                        ↓
                   证据与引用核验 → SSE → PostgreSQL 消息/研究成果

回答后：PostgreSQL 原文来源(memories) → Redis/Celery → 原子陈述与实体关系
       → 原文支持检查/旧记忆对账 → Neo4j 版本和来源图
```

Redis 在这里既是 Celery broker/backend，也缓存短期查询 embedding；它不是用户长期记忆数据库。`memory_search` 查 Neo4j，`knowledge_search` 查 ES。模型只给工具请求和参数，真正的数据库访问由服务端根据当前用户身份完成。

## 4. 记忆：必须能举具体例子

原话：**“我目前研究 WiFi CSI，下个月计划做室内定位实验。”**

```text
PostgreSQL messages: 用户原话、会话 ID、用户 ID、时间
PostgreSQL memories: raw_text=这句原话，source_message_id=那条消息 ID，status=pending→extracting→done
Neo4j Dialogue → Chunk → Statement 1: 用户目前研究 WiFi CSI；kind=FACT；status=active
                    └→ Statement 2: 用户计划下个月做室内定位实验；kind=PLAN；status=active
Statement 1 --MENTIONS--> 实体 WiFi CSI（Technology）
Statement 2 --MENTIONS--> 室内定位实验（Event/Topic，视抽取 Schema 而定）
```

上面是结构示意，真实节点 ID、标签和具体实体类型以每次模型抽取及图 Schema 为准。不能背成“每句话必定写图”：无信息、缺乏原文支持或抽取失败时不应当活跃事实写入。用户输入在回答成功后排后台任务，目的是让在线回答不等抽取；这不是另开一个线程和回答同时盲目写图。

### 两类“合并”分清楚

**实体去重**：`WiFi CSI` 与已有实体 `CSI` 可能指同一研究对象。先要求类别兼容，用名称/描述/向量相似度找候选，再让模型判断 same entity；服务端按阈值处理。名称完全一样也可能指不同对象，不能只看字符串。实体合并是把图里的对象 ID 指向同一个规范实体。

**陈述对账**：旧“我喜欢先看结论”，新“我更喜欢先看结论”可判断 NOOP；旧“我现在在杭州实习”，新“我之前说错了，现在在深圳实习”才可能 UPDATE；旧“我计划去深圳实习”，新“我已在深圳实习”不能仅因同一城市就自动将计划覆盖为事实；无法确定时 CONFLICT，用户确认。陈述对账决定事实版本是否活跃，和实体节点去重不是同一步。原话来源和旧版本保留，可追溯模型的判断。

**面试官问“同一轮一句话有三个事实怎么办？”**先拆成至多 24 条原子陈述；每条单独做来源支持、旧候选检索及对账，不用整句话与旧记忆直接相似度合并。拆错仍可能漏事实，保留原文和决策记录，靠错误样例回归和用户确认修复。

**面试官问“1000 条上限怎么处理？”**限制的是每用户活跃 Statement，不是 PG 原聊天 1000 条。超过后按重要性、置信度和时间等归档低优先级陈述，历史来源仍可保留；图节点还有整体硬预算。把所有 1000 条塞进 prompt 是错误做法，回答时只召回少量相关记忆。

## 5. RAG：每一个选择都要能解释

**为什么父子分块？** 全文或超大块容易把不同主题混在一个向量里，小块召回更精确，但直接把一个短句交给模型又缺上下文。先命中子块，再回取相应父块；引用记录文档与来源。默认 parent 1024/child 256/overlap 24 是项目配置，不是对所有文件都最优。Markdown 标题、PDF 页、CSV/XLSX 行具有不同结构，解析为文本时尽量保留定位信息；没有声称原始表格的计算语义全部保持。

**为什么 BM25 + 向量？** 专名、数字、缩写往往适合词项匹配，语义改写适合向量。两路原始分数没有统一量纲，默认 RRF 按名次累加 `1/(k+rank)`，避免手调不同来源分数的绝对比例；weighted 方案仍留作对照。`k=60` 主要控制名次平滑，不是 top 60 个答案。当前 100 文档标题明确题集里纯向量优于 RRF，因此不能宣称 RRF 实测全胜。默认选择 RRF 的理由是跨得分尺度的稳健性，需要更难的留出集再调参。

**Rerank 用了什么？** 代码支持用户配置 `rerank` 类型模型，对融合候选做精排；候选模型方案是 BAAI/bge-reranker-v2-m3，但本轮没有真实精排增益测试。面试应说“支持可选 Rerank”，不能说“采用该模型后提高了 xx%”。精排对 query 和候选一起打分，比首次召回贵，只用在前一小批候选。

**用户上传后立刻提问？** 文档入库异步，页面应观察 PG 状态；`pending/parsing` 阶段不能保证 ES 已有完整索引，`done` 后再提问。若 worker 崩溃，状态与索引可能短暂不一致；当前解析重试会按用户和来源删除旧块再重建，但 ES 与 PG 不是跨库原子提交，要用失败状态/重试和运维排查处理残留。

**怎么防幻觉？** 搜索强制用户过滤、证据带来源 ID；问题需要私人证据时，工具失败和空证据不会被包装成真实查询结果；Verifier 检查引用 ID 与关键事实是否被证据支持，失败修复一次仍不通过则拒答。模型判断本身会出错，因此这是降低风险的机制，不是数学证明或“零幻觉”。

## 6. Harness：面试官会沿着一次请求追问

**Q：Agent 怎样选工具？LangChain 和你写的代码各做了什么？**

> 当前对话模型收到工具名称、描述和 Schema；支持原生 function calling 时模型可以返回工具名及参数。LangChain 提供消息对象、`StructuredTool` 和模型接口；`orchestrator.py` 是我自己的控制循环：接收模型工具请求、把参数交给 `runtime.py` 校验和执行、把结果作为工具消息回灌，直到模型不给工具请求或达到上限。弱模型还有受限 ReAct 路径。两个工具可以在同一轮连续调用，能同时查文档和记忆。没有 LangGraph StateGraph、Multi-Agent 或默认启用 MCP。

**Q：模型让工具访问别人的数据怎么办？**

> 模型只提供如 query、top_k 的业务参数，用户身份来自已认证请求上下文。工具服务端把 user_id 和启用知识库作为数据库过滤条件；模型传入陌生 ID 不应绕过这个条件。聊天会话 ID 也在 SSE 响应头发出前校验所有权，陌生会话返回 404。

**Q：工具超时、返回空、重复调用怎么办？**

> `execute_tool` 先校验 Pydantic/JSON Schema、参数长度和结果长度，单次执行有超时；只对已知的只读工具做有限传输重试，未知或有副作用工具不盲重试。空结果标 empty，异常标 error，交还模型但不能编造结果。同一轮同工具同参数的结果缓存复用，重复空转或超过工具预算后退出。工具循环最多 5 次模型轮，配置的总工具调用次数另算，不是“最多思考五次”的同义词。

**Q：上下文无限增长吗？**

> 先读当前会话最近 20 轮，上限约 40 条用户和助手消息；再估算消息和工具 Schema 的 token。超预算按完整旧轮裁剪，当前问题、系统规则和工具定义不能被删；这些仍超预算就拒绝。当前没有自动把长期历史总结成摘要，所以不能说已实现无损长对话压缩。长期记忆只检索少量相关活跃陈述，不把整个 Neo4j 图放进 prompt。

**Q：为什么先核验再 SSE？那还是逐 token 流式吗？**

> 工具状态可在过程中通过 SSE 返回；正式答案需要缓存生成和核验后再发，否则客户端已经看见的错误答案无法撤回。SSE 仍是事件流，但需要证据的问题存在“核验前等待”，不能把它包装成每个 token 都即时、已核验地到达。

**Q：MCP 是否必要？**

> 当前核心工具是进程内 StructuredTool，RAG 和记忆都由本服务管理。MCP 适合跨进程/外部工具标准化接入，但会增加认证、权限、网络故障和工具可信度治理。当前项目有可选 MCP 接入，默认关闭；简历主线不靠它支撑。

## 8. 最可能被追问的“项目不成熟”问题

**Q：这是 ChatGPT 套壳吗？** 不是把用户消息直接转发模型。它有用户在线上传与异步索引、混合检索与来源回取、原文支持的记忆治理、后端受控工具循环、证据核验、研究成果版本，以及可复现的分层测试。不过真实用户规模和开放场景仍有限，不应自称工业级通用 Agent 平台。

**Q：为什么用 ES、Neo4j、PG 三个库？** PG 管事务和归属，ES 做全文+向量检索，Neo4j 做跨陈述的实体关系与来源遍历。图并不是为了让 Neo4j 同时替代 ES 的 BM25/向量融合；小规模应用也能用 PG 关系表实现，但这里用图是为多关系记忆和版本来源查询做实验，代价是跨库一致性复杂。

**Q：回答时记忆和知识库互相矛盾怎么办？** 文档是具体资料的来源，记忆是用户背景、计划和历史陈述，两者都可能过时。回答要标注各自来源及时间，不应默默用记忆覆盖文档。现有 Verifier 能检查本次证据的支持程度，但没有完整“跨多源权威级别与时间冲突仲裁”体系；发现冲突时应给出不确定性而不是硬选一方。

**Q：测试分数这么高是否说明设计已经最优？** 不说明。100 道标题题纯向量已全部在 top 5，几乎没有区分不同参数的空间。要验证分块、融合权重与 Rerank 的价值，需冻结独立难题集，分文档来源做训练/留出划分，逐题标 gold evidence，报告每类失败，而不是在同一小集上反复调到高分。

**Q：你最满意的改造是什么？** 建议讲“从会返回答案，到能说清证据从哪来及失败时怎样收敛”。用一个不存在备用数值的例子：工具检索返回文档但没有该字段，Verifier 不让模型从邻近数值猜测，最终提示无据；这在 30 题合成集和独立边界冒烟中测试过。再承认这些测试规模和题型仍有限。
