# 知忆 AI：RAG 质量控制与参数实验（2026-10-29）

本文只记录当前代码确实实现并验证过的行为。评测数据很小，参数结论是“暂不调整默认值”，不是“已找到最优参数”。

## 一次文档问答实际经过什么

```text
文件上传 → 原文件存储 + PostgreSQL 文档元数据 → Celery 解析
  → 按章节/页和句子划父块、子块 → 子块向量写 Elasticsearch
用户提问 → Agent 决定是否调用 knowledge_search
  → Elasticsearch 向量 kNN 和 BM25 各取候选 → 融合排序
  → 可选 Rerank → 子块命中后回取父块 → 带来源 ID 的证据
  → 模型生成候选答案 → 后端校验引用和证据支持情况
  → 通过才经 SSE 输出；不通过时最多修复一次，再失败则提示证据不足
```

原文件不存入 Neo4j。PostgreSQL 的 `documents` 记录文件名、类型、状态、归属知识库和原文件位置；Elasticsearch 的 `zhiyi_chunks` 存父子块、向量、`source_id`、`parent_id`、`user_id`、`kb_id` 和分块策略标记。Neo4j 保存从对话提取的长期记忆，是另一条数据链。主要入口为 `app/tasks/parse.py`、`app/core/rag/{parser,chunker,search,fusion}.py`、`app/core/agent/tools/builtin/knowledge.py` 和 `app/services/chat_service.py`。

## 幻觉控制：当前能做到什么

1. 私人资料问题由后端决定需要证据。知识库工具只按当前用户和已启用知识库过滤；工具空结果或失败不能作为“查到了”的证据。
2. 检索结果包含来源 ID、文档名和块 ID；知识库工具对过弱候选加一道相关度门控。答案中的未知 `K/M` 引用 ID 会被拒绝。
3. 候选答案先留在服务端，`verify_answer` 要求模型检查关键事实是否被本轮证据支持，特别是数字、时间、否定和“计划/已完成”的区别。失败最多修复一次；验证报错或仍不通过时返回证据不足提示。SSE 不会先展示未经校验的候选答案。
4. 这仍是**基于检索证据的约束**，不是现实真相证明。原文自身错误、OCR 缺失、模型误判、跨文档冲突及逐句引用不充分仍可能导致错误。当前没有独立人工真值库，也没有实测的全系统“幻觉率”。

使用真实聊天模型做过 3 个定向烟测：证据支持的数字答案通过；无证据支持的 99% 断言被拒绝；两份冲突证据下的断言被拒绝。3 个合成样例只说明这几条路径可执行，不能当成准确率。

## 混合检索权重怎样定

默认对向量与 BM25 各自的候选分数做 min-max 归一化，再算 `0.6 × 向量 + 0.4 × BM25`。权重是原有默认配置，**不是本次实验确定的最优值**。新 `FusionConfig` 使运行路径与离线评测共用同一融合函数；也可选 RRF，它按两路排名融合，减少对分数量纲的依赖。运行配置在 `app/config.py`，可用环境变量 `RAG_FUSION_METHOD`、`RAG_VECTOR_WEIGHT`、`RAG_RRF_K` 覆盖。改配置不会自动重建索引，改变分块或 Embedding 模型则需要重建相应文档索引。

`eval/tune_retrieval.py` 先固定同一批 ES 候选，再比较纯 BM25、纯向量、0.25/0.50/0.60/0.75 加权和 RRF@60；先取实际会送入问答的前 5 个子块，再折算其中出现的来源文档。同源文档的问题放在同一分组，避免在开发集和留出集之间泄漏；以留出集的成对差值和按文档组重采样的区间做审查。脚本只给候选建议，不自动写应用配置。

| 当前 10 篇/22 题 | 开发集 nDCG@5 | 留出集 nDCG@5 |
|---|---:|---:|
| 纯 BM25 | 0.9785 | 1.0000 |
| 加权 0.25/0.50 | 0.9785 | 1.0000 |
| 加权 0.60 | 0.9932 | 1.0000 |
| 加权 0.75 / RRF@60 | 0.9806 | 1.0000 |
| 纯向量 | 0.9830 | 1.0000 |

本次数据仅有 7 个相连来源组；分组切分后开发集 18 题、留出集 4 题。开发集 BM25 和低向量权重的 Recall@5 为 0.9722，其余为 1.0；留出集全部并列，所以**没有证据调整 0.6**，保留默认值兼容既有结果。`eval/results/retrieval-candidates-20261029-analysis.json` 为当次本地结果；结果目录默认不纳入 Git，任何人重新跑时应记录语料指纹、模型版本、索引版本与时间。

## 为什么这样分块

原策略是父块约 1024 token、子块约 256 token、子块重叠约 24 token。子块短一些便于准确命中，命中后回取父块保留回答所需上下文。本次增加章节/页边界、句子拼接和超长文本硬拆分，避免不同章节混在同一父块，也避免一个长句突破 token 限额。Markdown 标题与表格行会保留；Word 表格可读。滑动窗口仍用于子块边界，但不把固定窗口作为唯一切法。语义分块需要额外模型调用和稳定的边界评测；当前样本没有证据证明其收益足以覆盖成本，因此未引入。

用同一语料和真实 `bge-m3`/Elasticsearch 重新建立评测索引后得到：

| 父块 / 子块 / 重叠 | 混合 Recall@5 | 混合 MRR | 混合 nDCG@5 |
|---|---:|---:|---:|
| 1024 / 128 / 16 | 1.0000 | 0.9773 | 0.9841 |
| 1024 / 256 / 24 | 1.0000 | 1.0000 | 0.9944 |
| 1024 / 384 / 24 | 1.0000 | 1.0000 | 0.9944 |

这 10 篇文档都较短，评测 gold 只标“相关文档”，没有标相关段落或表格行。这里的分块实验沿用原评测口径：在召回候选中先按来源去重，再算前 5 篇相关文档；它与实际送给模型的前 5 个子块并不完全相同，因此只能作粗筛。它不能判断父子块是否真正提高证据定位，也不能区分 256 与 384。默认保留 256。要比较语义分块或父子策略，需要更长、多主题文档，并给相关块/行标注，另看答案有据率、上下文长度、入库耗时和查询时延。

## Excel、CSV 等文件怎样存和查

当前支持 `.pdf`、`.docx`、`.md/.markdown`、`.txt`、`.html/.htm`、`.csv`、`.xlsx`。CSV/XLSX 解析器把一行写成类似 `工作表 成绩 第 2 行 | 姓名: 张三 | 准确率: 92%` 的可检索文本；这段文字进入 ES 的子块与父块，原文件继续留在文件存储中，PG 记录元数据。因此“张三的准确率”可以命中对应行，回答引用仍指向原文档和块。真实 `bge-m3` 向量化与 ES 查询的隔离烟测已通过，并在结束后删除测试文档。

表格只按行做文本化，不支持 SQL 式跨行聚合、公式计算、复杂合并单元格或图表理解。`openpyxl` 读取公式的缓存值；没有缓存时可能为空。扫描版 PDF 也没有 OCR。这些问题需要独立的结构化表查询或 OCR 流程，不能声称当前 RAG 已经支持。

## 评测该分哪些步骤

1. **固定版本**：冻结语料、原文件、解析和分块配置、Embedding、BM25 配置、Rerank 与问答模型版本，记录数据指纹。文档新增或改写后保留旧版结果作基线，再用新版数据重跑。
2. **人工标注**：从真实问题中覆盖精确术语、同义改写、数字/表格、跨段、冲突、无答案、工具故障；标相关来源及具体证据块，并核对是否可回答。不同文档或用户的样例分组切开发、留出集，避免近重复问题泄漏。
3. **先测检索**：比较 Recall@K、MRR、nDCG@K；记录未命中样例，检查解析丢字、分块、召回、融合和 Rerank 各自在哪一步出错。先冻结检索候选调权重，再单独重建索引比块大小，避免把两个变量混在一起。
4. **再测生成**：人工逐条标答案正确、应答/拒答、关键断言是否有证据、引用是否指到正确证据。`eval/grounded_metrics.py` 可计算正确拒答率、错误拒答率、引用精确率/召回率、断言有据率、答案正确率，以及有标注时的工具选择、任务完成、延迟和 Token。缺失标注会输出 `null`，不会伪装成零分或满分。
5. **故障与回归**：测试空检索、过时文档、冲突来源、工具超时、未知引用、上传失败；参数候选须同时检查质量、P95 延迟、Token/调用费用和异常回退。确认收益后人工审查配置并回归，不让线上知识库变化自动改权重。

当前 10 篇/22 题可作回归集，但接近饱和、来源组少、没有答案和证据块真值，参考价值有限。下一步至少扩到多来源且难度分层的标注集，再保留一份真正未参与调参的留出集；固定的 100 题/20 来源门槛只是脚本的保守提示，**不是统计充分性的保证**。知识库内容持续变化时按语料版本监测样本分布与 Bad Case；新增领域、模板或文件格式，或更换分块、Embedding、Rerank 时重跑相同实验。若只是新增少量同类文档，也应抽样复核，不能直接假设旧权重仍最优。

## 复现命令

在 `api/` 下确保 Elasticsearch、Ollama 的 `bge-m3` 与 `eval/.env.eval` 中的 Embedding 配置可用。命令只改评测专用用户的 ES 数据；勿用真实用户 ID 做实验。

```bash
uv run --offline pytest -q
uv run --offline python -m eval.run_eval --only retrieval
uv run --offline python -m eval.chunk_ablation
uv run --offline python -m eval.tune_retrieval --collect --snapshot eval/results/retrieval-candidates.json
uv run --offline python -m eval.grounded_metrics eval/results/人工标注答案.jsonl
```

最后一条需要真实的人工标注文件；本轮没有完整答案标注集，因此**没有报告全系统答案准确率或幻觉率**。

## 面试时可以这样讲

> 我的 RAG 先按章节和句子切父子块，用子块做 BM25 与向量召回，命中后取父块给模型。权重现在默认向量 0.6、BM25 0.4，我把融合计算抽成一套服务端与评测共用的函数，并用冻结候选、按来源分组的开发/留出集与 RRF 对比。10 篇 22 题太小且接近饱和，留出集无法证明 0.6 更好，所以没有把它讲成调出的最优参数。答案必须经过引用 ID 和证据支持检查，失败可修复一次，仍失败就提示证据不足。表格上传时我保留工作表、行号和列名，Excel/CSV 可以像普通文档一样检索，但跨行计算不在这条 RAG 链路里。
