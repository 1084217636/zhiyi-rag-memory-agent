# 知忆 AI 面试讲解与实现边界

## 项目定位

知忆现在讲成“个人研究助手”：用户把资料放进自己的知识库，围绕一个主题提问并形成可编辑、有来源快照的研究笔记；长期记忆帮助跨会话找回用户背景。重点是把 RAG、记忆和 Agent 执行链路接成能被约束、检查和复现的应用。当前没有做多 Agent 编排，也没有把 CoT 思维链暴露给用户；MCP 是可选接入，默认关闭，需要明确 allowlist。

## 3 分钟项目介绍

> 我做的是一个个人研究助手，主要解决两个连续问题：一是用户上传的资料怎么被可靠检索并带来源回答；二是跨会话时怎样找回用户明确表达过的长期信息。系统除了聊天问答，还可以把回答和引用保存成研究成果，用户之后能重新打开并编辑版本。
>
> 文档上传后 API 把解析任务交给 Celery。Worker 支持 PDF、DOCX、Markdown、TXT、HTML、CSV、XLSX，按格式抽文本并保留页码/表格行等来源信息，再按标题/段落组织父块并切成更小的子块。ES 对子块分别做向量和 BM25 召回，当前默认用 RRF 合并排名；如果用户配置了 rerank 模型，再对最多 20 个候选做精排，最后从命中的子块回取父块上下文，引用仍指向原文档和来源位置。图像、扫描件 OCR、PPT、压缩包和视频目前不在解析器支持范围。
>
> 长期记忆不是把整段对话都塞进 Neo4j。PostgreSQL 的 `messages` 保留对话，用户输入原文另写 `memories`，记录 `raw_text`、来源消息 ID、处理状态和 Neo4j 对话 ID。Celery 对单条原文先拆原子陈述，再抽实体、关系和事件；先用模型核对抽取是否受原文支持，然后对每条陈述找最多 8 条相似旧陈述做 ADD、NOOP、UPDATE、CONFLICT 或 SKIP 判定。后端验证模型引用的旧 ID、置信度和更正信号；更新保留旧陈述并用 SUPERSEDES 连接，不确定的进入待确认，不覆盖旧事实。Neo4j 保存 Dialogue→Chunk→Statement 的来源链和实体关系边，用户记忆默认最多 1000 条活跃陈述，图节点另有 10000 的硬预算。
>
> 问答时，后端先取当前会话最近 20 轮，也就是最多 40 条 user/assistant 消息，再按问题召回记忆背景并构造可用工具。LangChain 提供消息和工具结构，Python 编排原生工具调用循环；最多 8 次工具调用，单次工具、模型和整轮都有超时，重复的同名同参工具结果会缓存。模型若要查资料或记忆，服务端校验工具 Schema、权限、大小和调用预算后执行，将结果回灌模型。需要私人证据的问题由服务端触发检索要求；最终答案会检查引用 ID 和关键事实是否受证据支持，失败时有限修复，仍失败就回退为证据不足。通过检查后才把答案和引用以 SSE 发给网页。网页还可以把该答案和引用快照保存到 PostgreSQL 的 `research_artifacts`，更新时用版本号防止覆盖。
>
> 我用离线集和单元测试验证关键策略，当前 API 测试 90 项通过，前端构建和隔离数据库迁移通过。RAG 与记忆回归集各有 100 条查询表述，但分别只覆盖 20 个文档问题组和 19 个记忆事实组；这些变体用来检查措辞鲁棒性，不能当成 100 个独立事实或统计显著性证据。没有真实模型凭据时，不报新一轮检索、Rerank 或生成质量成绩。该项目是个人资料助手，不是企业级多租户平台。

## 从上传到研究成果：完整用户流程

```text
网页上传文档
  → FastAPI 写 PostgreSQL 文档状态，Celery 接解析任务
  → Worker 解析文本/表格，父子分块，ES 建 BM25 与向量索引
  → 用户开会话提问
  → 取最近 20 轮消息 + 问题相关记忆背景
  → Agent 选择知识库、记忆或其他已授权工具
  → 后端校验工具参数、用户范围、超时、结果长度与调用预算
  → 工具结果回到模型继续回答；满足停止条件后进入证据校验
  → 引用和关键事实验证；有限修复，失败则安全提示
  → SSE 发出答案、工具状态和引用；PostgreSQL 保存对话
  → 用户点“保存为研究成果”，PostgreSQL 保存正文、引用快照、来源快照和版本
```

## 记忆怎么存：一条输入的实际例子

用户说：**“我目前在研究 WiFi CSI，打算下个月做一个室内定位实验。”**

1. PostgreSQL `messages` 先保存原始用户消息。问答成功后，`Memory` 另保存一条来源记录：

```text
memories
id                 = 8b…
user_id            = 当前用户 UUID
raw_text           = 我目前在研究 WiFi CSI，打算下个月做一个室内定位实验。
source             = auto
source_message_id  = 原始 messages.id
status             = pending → extracting → done（失败则 failed）
graph_dialogue_id  = Neo4j 来源 Dialogue 节点 ID
graph_stats        = 本次抽出的陈述/实体/关系数量
```

2. Celery 把一个复合句拆成独立候选，例如：`用户目前研究 WiFi CSI`（FACT）、`用户计划下个月做室内定位实验`（PLAN）。这不是单纯正则切句：LLM 做陈述和三元组结构化抽取，Pydantic 限字段类型/分数范围，服务端再次让模型对照原文逐条给出受支持的候选 ID。校验失败的候选不会当作已确认事实写入。
3. Neo4j 图中，来源是 `Dialogue`，其下有 `Chunk`，再指向 `Statement`；陈述通过 `MENTIONS` 连到实体，实体之间用带谓词和时间属性的 `RELATION` 表示关系。`Entity.type` 是对象类别，例如 Person、Organization、Technology，不是“实体/关系/事件”这几种数据块；关系的谓词单独放在 `RELATION.predicate`，事件是独立 `Event` 节点。`Statement` 还保存 `memory_kind/status/confidence/valid_at/invalid_at/dialog_at` 等治理与时间字段。不能把所有时间都压到一个“最新值”：不同时间发生的经历可以同时成立。

## 去重和合并：判什么、用什么判

去重分成两类，不能混成“主客体相同就覆盖”：

1. **实体去重**解决图里的同一个对象是否有多个节点。先要求实体类型相同，再用名称编辑相似度、名称向量相似度或包含关系筛候选；候选才交给模型做 same-entity 判断，置信度至少 0.80 才合并。精确同名同类型仍不会无条件合并：稳定的“用户”可复用，其他对象通常还要求描述一致；否则保留两个节点。批内和 Neo4j 历史实体各有一轮判断，合并后把实体 ID 重定向到保留节点，别名、描述和 mention 计数合并。
2. **陈述对账**解决新记忆是否新增、重复、更新或冲突。先对每条原子陈述计算 embedding/文本相似度，取相似度至少 0.25 的最多 8 条旧陈述作为候选；相似度只负责找候选，不能证明相同。完全规范化后相同且类型相同的静态陈述可直接 NOOP；否则让模型在固定枚举 ADD/NOOP/UPDATE/CONFLICT/SKIP 里选，并只能引用候选旧 ID。后端再验证 ID、置信度、记忆类型和明确更正信号。

**例子 A：不合并，保留两条。**旧记忆“用户在研究 WiFi CSI”；新记忆“用户计划学习视觉 SLAM”。两者都提到研究/学习，但对象和含义不同。相似召回即使找到前者，模型也应选 ADD，不能因为都是研究主题就合并。

**例子 B：重复，不新增活跃陈述。**旧“用户喜欢先看结论”，新“用户更喜欢先看结论”。如果对账模型确认含义相同且没有新信息，选 NOOP；新来源仍保留为来源链，旧活跃陈述不被覆盖并增加支持计数。

**例子 C：明确更正才更新。**旧“我在西安实习”；新“刚才说错了，我实习地点不是西安，是深圳”。只有模型选择同一事实槽位的 UPDATE、引用真实旧 ID、置信度不低于 0.9、文本有明确更正信号且类型匹配，后端才把新陈述设 active、旧陈述标 superseded，并连 `SUPERSEDES`。原始来源都保留。

**例子 D：不确定就待确认。**旧“用户准备去深圳实习”；新“用户现在在深圳实习”。“准备去”不代表已经开始，计划不能自动升级为事实；若模型不确定是进展还是纠正，新记录为 `pending_confirmation`，由用户选择保留两条、替换或拒绝。

**复合句怎么避免一条覆盖多条？**先把一轮原文拆成至多 24 条原子陈述，每条单独跑来源支持核对和候选匹配；陈述 ID 按来源消息和序号稳定生成，Celery 重投不会创建另一批新 ID。模型最多提出 3 个 target ID，后端验证均来自该用户的候选集合。错误拆分仍可能造成漏抽/误抽，因此保留原文、记录决策原因和待确认项，并用“计划/更正/否定/多事实句”评测集测误合并；这不是零错误保证。

**容量怎么控制？**当前配置默认每用户最多 1000 条活跃 Statement；超出时按 `importance × confidence`、创建时间等排序归档低优先级陈述，不物理删除历史来源；计划与推断分别有 TTL。Neo4j 另设全图节点数上限 10000。达到图硬上限时不写部分图，任务失败并保留 PostgreSQL 原文供重试/清理。这是项目级策略，不是行业统一阈值。

## RAG 的关键存储和选择理由

- **PostgreSQL**：用户、知识库、文档状态、会话/消息、记忆来源、Agent Trace、研究成果与版本。业务状态和审计需要事务与归属查询。
- **Elasticsearch**：当前解析器支持 PDF、DOCX、Markdown、TXT、HTML、CSV、XLSX；索引文档父子块、向量、BM25 字段、文档/知识库/用户 ID、来源和页码/块 ID。表格先按行/单元格组织成可检索文本，保留来源位置字段；它承担检索，不作为原始业务状态事实库。当前不支持任意压缩包或视频内容理解。
- **Neo4j**：Dialogue、Chunk、Statement、Entity、Event 节点；`HAS_CHUNK`、`HAS_STATEMENT`、`MENTIONS`、`RELATION`、`SUPERSEDES` 等边。图优势是按实体遍历关系和证据来源，不是自带 BM25/向量融合；实体文本/向量候选搜索和 Neo4j 邻居遍历是不同阶段。
- **Redis/Celery**：Redis 是 Celery broker/backend，也保存短期、按用户和 Embedding 模型隔离的查询向量缓存（默认 300 秒）。只缓存 query embedding，不缓存文档正文、检索命中或引用，所以文档更新/删除不会把旧正文或别人的内容从缓存返回；Redis 缓存故障时回源模型。Celery worker 拿解析/记忆任务，业务原文仍在 PostgreSQL，队列不是唯一存储。

RAG 的父子分块是为“小块更容易命中，父块给模型完整上下文”。当前配置 parent 1024、child 256、overlap 24 tokens；这是项目默认值，不是通用最优。融合从 weighted（向量 0.6、BM25 0.4）改为默认 RRF，`k=60`：两路相关性分数尺度不同，RRF 按各自名次累加 `1/(k+rank)`，不用把 Elasticsearch 的 BM25 分数和向量分数硬归一到同一量纲。weighted 仍保留作对照，`api/eval/tune_retrieval.py` 用同一冻结候选比较纯向量、纯 BM25、不同权重和 RRF。当前只有离线函数测试，100 条变体集尚未连真实 Embedding/ES 重跑，因此 RRF 是基于分数尺度稳定性的默认工程选择，不声称实测效果胜过 weighted。

Rerank 的评测候选配置是 `BAAI/bge-reranker-v2-m3`，通过兼容 `/rerank` 的 SiliconFlow/Jina/Cohere 网关调用；系统运行时仍由用户的 `type=rerank` 模型配置决定是否启用。当前没有有效凭据，面试只能说“支持可配置 Rerank，评测候选为 BAAI/bge-reranker-v2-m3”，不能说本轮已实测它的增益。Rerank 把 query 与候选文本一起交给 cross-encoder 打相关度，慢于向量召回，所以只精排初召回的少量候选，而不是全库。

## Harness 与后端约束：说清楚代码现在做什么

- LangChain `StructuredTool`、消息类型和模型接口负责标准化输入输出；**没有 LangGraph StateGraph，也没有 Multi-Agent**。工具循环是项目自己的 Python 控制流，强模型走原生 function calling，弱模型走受限 ReAct 解析。
- 工具注册由 `ToolSpec` 管名称/描述/构造器/默认启用；每个工具有 Pydantic 参数模型，拒绝多余字段、空 query 或超长参数。
- `execute_tool` 限参数/结果长度、单次超时；只对白名单只读工具做有限传输重试，不盲重试未知或有副作用工具。工具失败返回明确 error 状态，不伪造结果。
- 当前每轮最多 8 次工具调用，模型单次/整轮有 timeout。相同工具+规范化参数在一次 Agent run 内缓存；重复空转到阈值会停。
- 每次模型调用、工具调用、Verifier 有 Trace span，保存耗时、状态、token 用量；默认不保存完整敏感内容。Redis Lua 做每用户速率与并发准入，Redis 不可用时 fail closed。
- 短期上下文取最近 20 轮 = 最多 40 条消息，再用 `cl100k_base` 估算 system/history/tools 总 token。超预算时整轮裁剪较旧对话；当前**没有自动摘要/无限上下文压缩**。当前问题、系统提示和工具定义仍超限时拒绝本轮，要求缩短输入。
- 工具调用不是模型“想几轮就想几轮”：有工具时循环请求模型；模型返回无工具调用时结束。到达 8 次调用或循环上限仍未完成，会停止继续执行并走受限退出提示/最终处理，不保证继续无限找资料。
- 证据校验判断“回答是否被本次检索证据支持”，不是证明网络事实真实。引用不存在、证据不足、冲突或 verifier 失败会有限修复；仍失败返回固定安全提示。SSE 在校验后发正式答案，避免先把未核验回答流出去。

## 当前评测与真实状态

本轮运行：`python3 -m compileall -q api/app` 通过；`pytest api/tests -q` 为 **90 passed**；前端构建、Compose 基础与 observability overlay 配置检查通过；`alembic upgrade head` 成功，已在隔离 PostgreSQL 容器看到 `research_artifacts` 表与 FK。实际 HTTP 验收完成成果创建/版本更新/旧版本冲突；健康接口检查 PostgreSQL、ES、Neo4j、Redis 均可连接。新增 `/api/metrics` 暴露低基数 HTTP 请求数和延迟直方图，Prometheus overlay 抓取配置已写好。真实模型 RAG、Rerank 对比和 100 条候选生成仍需有效模型凭据，不能宣称已跑通或有质量提升。

`api/eval/fixtures/gold/retrieval_100.json` 与 `memory_retrieval_100.json` 由 `expand_qa_fixtures.py` 从已审阅的原始问题扩成 100 条措辞回归题；RAG 有 20 个问题组，记忆有 19 个事实组，组内题目相关，不能当 100 个独立知识点。它主要测检索对措辞变化是否稳定。专业质量结论仍要新增独立文档/事实，人工标注 query→gold evidence，按来源组切分开发/留出集，再对照 Recall@K、MRR/nDCG、引用支持率、拒答率、P95 延迟和 token 成本。当前新 100 题尚未跑真实向量检索，所以无新成绩。

## 简历建议版本

- **知忆 AI 个人研究助手**：基于 FastAPI、LangChain、Celery、Elasticsearch、Neo4j 与 PostgreSQL，实现多格式资料解析、父子分块、BM25/向量融合与可选 Rerank，支持带来源回答及研究成果版本化保存。
- 构建跨会话记忆流水线：保留 PostgreSQL 原文，由 Celery 抽取陈述/实体/关系/事件，增加来源支持核验、候选相似召回及重复/更正/冲突治理，在 Neo4j 保留来源图、版本关系和活跃记忆预算。
- 实现受控 Agent 执行链：Schema 与权限校验、超时/有限重试、步骤和 token 预算、Trace 与基于证据的答案验证；使用离线检索/记忆集和自动化测试定位召回、误合并与工具失败问题。

这些简历点仅描述此新副本当前代码；每项中“完整多格式范围”应以解析器现支持格式为准，当前不能说成任意格式或多模态都支持。
